# Лабораторные работы: RAG, микросервисная архитектура и Kubernetes

## Общая информация

В рамках курса необходимо выполнить **3 последовательные лабораторные работы**, объединённые общей тематикой:

1. **Лабораторная работа №1** — разработка собственной RAG-системы.
2. **Лабораторная работа №2** — разработка микросервисного backend-приложения.
3. **Лабораторная работа №3** — контейнеризация и оркестрация приложения из лабораторной работы №2.

Лабораторные работы выполняются **последовательно**: результаты предыдущей лабораторной используются в следующей.

---

# Лабораторная работа №1. Разработка собственной RAG-системы

## 1. Цель работы

Цель лабораторной работы — изучить принципы построения современных систем **Retrieval-Augmented Generation (RAG)** и самостоятельно реализовать полноценный pipeline поиска информации и генерации ответов на основе внешних источников данных.

Основной акцент лабораторной работы — **исследовательский подход**.

Необходимо не просто собрать работающий RAG из готовых компонентов, а исследовать влияние различных архитектурных решений на качество получаемых ответов.

---

## 2. Постановка задачи

Необходимо разработать собственную RAG-систему, которая способна отвечать на вопросы пользователя на основе заранее собранного набора документов или других источников информации.

В качестве предметной области можно выбрать практически любую тематику.

### Примеры предметных областей

* техническая документация;
* документация по программным библиотекам;
* законодательство;
* научные статьи;
* книги;
* университетские материалы;
* документация компьютерных игр;
* медицинская или биологическая литература;
* финансовые документы;
* документация open-source проектов;
* Wikipedia или другие открытые источники;
* набор HTML/PDF/Markdown/TXT документов.

Предметная область должна быть достаточно содержательной, чтобы на её основе можно было сформировать набор вопросов для проверки качества системы.

# 3. Требования к RAG-системе

Разрабатываемая система должна включать основные этапы RAG pipeline.

Минимальная архитектура:

```text
                    ┌─────────────────┐
                    │    Источники    │
                    │ Web / PDF / MD  │
                    │ Docs / API etc. │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │     Grabber     │
                    │ Сбор документов │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │ Data Processing │
                    │ Очистка данных  │
                    │   Chunking      │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │   Embeddings    │
                    │ Векторизация    │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │  Vector Store   │
                    │ Vector Database │
                    └────────┬────────┘
                             │
                    User Query
                             │
                             ▼
                    ┌─────────────────┐
                    │    Retriever    │
                    │ Поиск документов│
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │    Reranker     │
                    │ Переранжирование│
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │    Filters      │
                    │ Фильтрация      │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │       LLM       │
                    │ Генерация ответа│
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │     Answer      │
                    │ Ответ + Sources │
                    └─────────────────┘
```

# 4. Автоматический сбор данных

Обязательной частью лабораторной работы является реализация **автоматического grabber'а данных**.

Необходимо написать программу, которая самостоятельно получает данные из выбранных источников.

Ручное скачивание нескольких документов и помещение их в папку **не считается автоматическим grabber'ом**.

### Grabber должен уметь:

* получать данные из источника;
* определять новые/изменённые документы;
* сохранять полученные данные;
* обрабатывать ошибки;
* не создавать дубликаты;
* при необходимости сохранять metadata документа;
* запускаться повторно без необходимости ручной подготовки данных.

### Примеры

Для Web:

```text
Website
   ↓
Crawler
   ↓
HTML
   ↓
Parser
   ↓
Clean text
   ↓
Documents
```

Для GitHub:

```text
Repository
   ↓
Git/API
   ↓
Markdown / Code / Docs
   ↓
Parser
   ↓
Documents
```

Для PDF:

```text
PDF source
   ↓
Downloader
   ↓
PDF parser
   ↓
Text
   ↓
Documents
```

# 5. Обработка данных

После получения документов необходимо реализовать preprocessing pipeline.

Минимально необходимо рассмотреть:

* очистку текста;
* удаление ненужной информации;
* нормализацию текста;
* разбиение документов на chunks;
* сохранение metadata.

Например:

```text
Document
    ↓
Cleaning
    ↓
Normalization
    ↓
Chunking
    ↓
Metadata
    ↓
Embeddings
```

### Metadata

Желательно сохранять:

```json
{
  "source": "documentation",
  "url": "...",
  "title": "...",
  "section": "...",
  "document_id": "...",
  "updated_at": "..."
}
```

---

# 6. Chunking

Необходимо исследовать влияние стратегии разбиения документов на качество поиска.

Минимально рекомендуется сравнить несколько вариантов:

* фиксированный размер chunk;
* chunk с overlap;
* разбиение по абзацам;
* разбиение по заголовкам/секциям.

Необходимо провести эксперимент и показать, какой вариант оказался наиболее эффективным.

---

# 7. Embeddings

Для преобразования текста в векторное представление необходимо использовать embedding-модель.

Допускается использование любых **бесплатных моделей**.

Например:

* Sentence Transformers;
* BGE;
* E5;
* другие открытые embedding-модели.

Необходимо указать:

* название модели;
* размерность embedding;
* язык/языки;
* причину выбора;
* результаты экспериментов.

---

# 8. Vector Database

Для хранения embeddings необходимо использовать векторное хранилище.

Можно использовать, например:

* FAISS;
* Chroma;
* Qdrant;
* Milvus;
* Weaviate;
* Elasticsearch/OpenSearch с vector search;
* другое решение.

Выбор технологии необходимо обосновать.

---

# 9. Retriever

Система должна использовать механизм поиска релевантных документов.

Необходимо реализовать retrieval и исследовать его параметры.

Например:

```text
Query
  ↓
Embedding
  ↓
Vector Search
  ↓
Top-K documents
```

Необходимо исследовать влияние параметра `K`.

Например:

```text
K = 3
K = 5
K = 10
K = 20
```

Результаты необходимо сравнить.

---

# 10. Reranker

Для повышения качества поиска рекомендуется использовать **reranker**.

Reranker получает результаты первичного поиска и повторно сортирует их по релевантности.

Пример:

```text
Query
  ↓
Retriever
  ↓
Top-20
  ↓
Reranker
  ↓
Top-5
  ↓
LLM
```

Необходимо сравнить:

```text
Retriever
vs
Retriever + Reranker
```

и показать влияние reranking на качество системы.

---

# 11. Фильтрация

Необходимо предусмотреть механизмы фильтрации контекста.

Например:

* удаление нерелевантных chunks;
* threshold по similarity score;
* ограничение количества документов;
* фильтрация по metadata;
* удаление дубликатов;
* фильтрация слишком коротких результатов.

Пример:

```text
Retriever
   ↓
20 documents
   ↓
Similarity threshold
   ↓
Deduplication
   ↓
Reranker
   ↓
5 documents
   ↓
LLM
```

---

# 12. Генерация ответа

Для генерации ответа необходимо использовать LLM.

Допускается использование бесплатных/open-source моделей.

Например:

* Llama;
* Qwen;
* Mistral;
* Gemma;
* другие доступные модели.

LLM должна получать:

```text
System Prompt
+
User Query
+
Retrieved Context
```

и на основании этого формировать ответ.

---

# 13. Защита от hallucination

RAG-система должна уметь корректно обрабатывать ситуацию, когда информации в базе недостаточно.

Например:

```text
Если ответ невозможно найти
в предоставленном контексте,
необходимо сообщить пользователю,
что информации недостаточно.
```

Желательно добавить ссылки/источники, на основании которых был сформирован ответ.

Пример:

```text
Ответ:
...

Источники:
- documentation/page1
- documentation/page5
```

# 14. Исследовательская часть

**Это наиболее важная часть лабораторной работы.**

Недостаточно просто реализовать pipeline.

Необходимо провести эксперименты и исследовать, как различные компоненты влияют на качество системы.

Минимально рекомендуется исследовать:

| Компонент     | Эксперимент                   |
| ------------- | ----------------------------- |
| Chunking      | разные размеры chunks         |
| Chunk overlap | несколько значений            |
| Embeddings    | минимум 2 модели              |
| Retriever     | разные значения Top-K         |
| Reranker      | с reranker / без reranker     |
| Filtering     | разные thresholds             |
| LLM           | минимум 2 модели или 2 режима |
| Prompt        | минимум 2 варианта            |

Не обязательно исследовать абсолютно все пункты, если есть обоснованная замена.

Главное — показать **исследовательский подход**.

# Лабораторная работа №2. Микросервисное приложение

## 1. Цель работы

Цель лабораторной работы — разработать полноценное backend-приложение на основе **микросервисной архитектуры**.

Необходимо самостоятельно спроектировать систему, разделив её функциональность на независимые backend-сервисы.

---

# 2. Основное требование

Приложение должно содержать **минимум 5–6 backend-микросервисов**.

> База данных, frontend/UI, API Gateway и reverse proxy не считаются полноценными бизнес-микросервисами.

То есть проект только с:

```text
Frontend
Backend
Database
```

не соответствует требованиям лабораторной работы.

---

# 3. Пример архитектуры

Допускается выбрать любую предметную область.

Например, система управления онлайн-магазином:

```text
                    ┌──────────────┐
                    │ API Gateway  │
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ▼                  ▼                  ▼
 ┌────────────┐     ┌────────────┐     ┌────────────┐
 │Auth Service│     │User Service│     │Product     │
 │            │     │            │     │Service     │
 └────────────┘     └────────────┘     └────────────┘
        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
       ┌──────────┐  ┌───────────┐ ┌───────────┐
       │  Order   │  │ Payment   │ │Notification│
       │ Service  │  │ Service   │ │  Service  │
       └──────────┘  └───────────┘ └───────────┘
```

Это только пример.

Можно выбрать:

* систему бронирования;

* собственную предметную область.

# 4. Требования к микросервисам

Каждый микросервис должен иметь:

* собственную ответственность;
* отдельный API;
* собственную бизнес-логику;
* возможность независимо запускаться;
* отдельную конфигурацию;
* обработку ошибок;
* logging.

Пример:

```text
User Service
    ↓
Работа с пользователями

Order Service
    ↓
Создание и управление заказами

Payment Service
    ↓
Платежи

Notification Service
    ↓
Отправка уведомлений
```

---

# 5. Независимость сервисов

Необходимо избегать архитектуры:

```text
Service A
   ↓
Service B
   ↓
Service C
   ↓
одна огромная Database
```

Микросервисы должны быть логически разделены.

Желательно использовать подход:

```text
Service A → Database A

Service B → Database B

Service C → Database C
```

Использование одной БД допускается только при наличии архитектурного обоснования.

---

# 6. Взаимодействие между сервисами

Необходимо реализовать взаимодействие между микросервисами.

Можно использовать:

### Синхронное взаимодействие

```text

gRPC
```

### Асинхронное взаимодействие

```text
RabbitMQ
Kafka
NATS
Redis Streams
```

Желательно реализовать хотя бы один сценарий асинхронного взаимодействия.

Например:

```text
Order Service
      │
      │ OrderCreated
      ▼
   RabbitMQ
      │
      ▼
Notification Service
```

# Лабораторная работа №3. Docker и Kubernetes

## 1. Цель работы

В третьей лабораторной необходимо взять приложение из **лабораторной работы №2**, контейнеризировать его и развернуть с использованием системы оркестрации контейнеров.

Допускается использовать:

* Kubernetes;
* Minikube.

---

# 2. Docker

Каждый backend-микросервис должен быть контейнеризирован.

Например:

```text
Auth Service
      ↓
Docker Image

User Service
      ↓
Docker Image

Order Service
      ↓
Docker Image

...
```

Для каждого сервиса необходимо предоставить `Dockerfile`.

---

# 3. Dockerfile

Dockerfile должен быть оптимизирован.

Необходимо учитывать:

* небольшой размер image;
* использование `.dockerignore`;
* caching слоёв;
* отсутствие секретов внутри image;
* запуск приложения не от root, если это возможно;
* корректный CMD/ENTRYPOINT.

Пример структуры:

```text
service/
├── Dockerfile
├── .dockerignore
├── requirements.txt
└── src/
```

---

# 4. Docker Compose

Перед Kubernetes рекомендуется проверить приложение через Docker Compose.

Пример:

```text
docker-compose.yml

        ┌──────────────┐
        │ API Gateway  │
        └───────┬──────┘
                │
     ┌──────────┼──────────┐
     ▼          ▼          ▼
   Auth       User       Order
 Service     Service     Service
     │          │          │
     ▼          ▼          ▼
   DB/Auth    DB/User    DB/Order
```

Compose должен позволять поднять всю систему одной командой.

Например:

```bash
docker compose up --build
```

---

# 5. Kubernetes

Необходимо подготовить Kubernetes manifests.

Минимально рекомендуется использовать:

```text
Deployment
Service
ConfigMap
Secret
```

Для каждого backend-сервиса должен существовать Kubernetes Deployment.

Например:

```text
k8s/
├── namespace.yaml
├── auth/
│   ├── deployment.yaml
│   └── service.yaml
├── user/
│   ├── deployment.yaml
│   └── service.yaml
├── order/
│   ├── deployment.yaml
│   └── service.yaml
├── payment/
│   ├── deployment.yaml
│   └── service.yaml
├── notification/
│   ├── deployment.yaml
│   └── service.yaml
├── gateway/
│   ├── deployment.yaml
│   └── service.yaml
├── configmap.yaml
└── secret.yaml
```

Структура может отличаться.

---

# 6. Deployment

Для каждого сервиса необходимо создать Deployment.

Deployment должен описывать:

* Docker image;
* количество replicas;
* container port;
* environment variables;
* resources;
* health checks.

Например:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: user-service
spec:
  replicas: 2
  selector:
    matchLabels:
      app: user-service
  template:
    metadata:
      labels:
        app: user-service
    spec:
      containers:
        - name: user-service
          image: user-service:latest
          ports:
            - containerPort: 8000
```

---

# 7. Kubernetes Service

Для взаимодействия между сервисами необходимо использовать Kubernetes Services.

Например:

```text
order-service
      │
      │ HTTP
      ▼
payment-service
```

В Kubernetes:

```text
http://payment-service:8000
```

Сервисы не должны обращаться друг к другу через `localhost`.

---

# 8. ConfigMap

Конфигурационные параметры необходимо вынести из Docker image.

Например:

```text
DATABASE_HOST
DATABASE_PORT
LOG_LEVEL
SERVICE_URL
```

должны задаваться через environment variables / ConfigMap.

---

# 9. Secrets

Пароли, токены и другие секретные значения нельзя хранить непосредственно в исходном коде.

Например:

```text
DATABASE_PASSWORD
JWT_SECRET
API_KEY
```

не должны находиться в Git в открытом виде.

Для Kubernetes необходимо использовать `Secret`.

---

# 10. Health Checks

Каждый сервис должен иметь health endpoints.

Например:

```text
/health
/ready
```

В Kubernetes необходимо использовать:

```text
livenessProbe
readinessProbe
```

Пример:

```yaml
livenessProbe:
  httpGet:
    path: /health
    port: 8000

readinessProbe:
  httpGet:
    path: /ready
    port: 8000
```

---

# 11. Resource Limits

Для контейнеров необходимо задать ограничения ресурсов.

Например:

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

Конкретные значения должны зависеть от вашего приложения.

---

# 12. Масштабирование

Необходимо продемонстрировать возможность горизонтального масштабирования хотя бы одного сервиса.

Например:

```bash
kubectl scale deployment order-service --replicas=3
```

После этого:

```text
             ┌─ order-service
             │
Request ─────┼─ order-service
             │
             └─ order-service
```

## Главное

Лабораторные работы оцениваются не только по принципу **«код запускается»**.

Высоко оцениваются:

* самостоятельность;
* понимание используемых технологий;
* качество архитектуры;
* эксперименты;
* сравнение альтернатив;
* анализ результатов;
* корректная документация;
* способность объяснить принятые решения.

**Цель лабораторных — не просто собрать работающий проект, а показать понимание современных подходов к разработке AI-систем и распределённых приложений.**
